## Custom fields

The observed Request contains deployment-specific `u_*` fields. These are not assumptions of the generic MCP core. Examples of custom concepts that can appear include customer aliases, legal entity, project/project-task references, request flags, update indicators, and manual-close flags.

A generic parser can preserve these as `CustomFieldDTO` entries without promoting them to stable `RequestDTO` properties.

## Proposed structured representation

```python
@dataclass
class RequestDTO:
    sys_id: str
    number: str
    record_type: str = "sc_request"

    requested_for: str | None = None
    location: str | None = None
    parent: str | None = None

    contact_type: str | None = None
    approval: str | None = None
    request_state: str | None = None

    custom_fields: list[CustomFieldDTO] = field(default_factory=list)
    activities: list[ActivityDTO] = field(default_factory=list)
```

This is an XRAY/proposed representation, not yet a runtime API guarantee.

## Relationships / related lists

The Request is the aggregate/root record for one or more Requested Items.

The classic form exposes relationship surfaces including:

- Requested Items (`sc_req_item`) — direct child records linked through their `request` field
- Approvers
- Group approvals
- deployment-specific service-order relationships

The stable catalog relationship is:

```text
REQ / sc_request
  └── Requested Items[] / sc_req_item
          └── downstream fulfillment records
```

In the observed form, the Requested Items related list is identifiable through the relationship key:

```text
sc_request.sc_req_item.request
```

This is strong structural evidence for a generic `REQ → RITM[]` relationship parser without depending on a tenant-specific record number.

## Activity stream

The Request uses the standard task-style activity/journal surface. Available activity filters include concepts such as:

- comments
- work notes
- assigned-to changes
- attachments
- configuration-item changes
- autogenerated/correspondence email events
- impact
- opened-by events
- priority
- state

As with other record types, the current `comments` and `work_notes` textareas are journal inputs and must not be mistaken for historical entries.

## Parsing strategy

```text
REQ number
   ↓
resolve sc_request
   ↓
GET sc_request.do?sys_id=<id>
   ↓
validate sc_request form structure
   ↓
parse stable fields
   ├── reference display values
   ├── choice display values
   ├── currency/display values
   ├── custom fields separately
   └── activity stream
   ↓
RequestDTO
```

## Discovery notes

The classic Request page is directly parseable from authenticated server-rendered HTML. Once the `sys_id` is known, navigation wrapper parameters are not needed; `sc_request.do?sys_id=<id>` is the canonical read target.

The form provides several useful generic parsing conventions:

```text
sc_request.<field>                     → raw/internal value
sys_display.sc_request.<field>         → human-readable reference value
sys_readonly.sc_request.<field>        → rendered readonly field/choice
sys_original.sc_request.<field>        → original value used by the form
```

For agent-facing structured output, prefer the human-readable display value while retaining raw values only where they add semantic value.

The Request is notably different from WO/WOT: its primary role is aggregation and approval of catalog demand. Its most important structural relationship is therefore its child Requested Items rather than execution tasks directly.
