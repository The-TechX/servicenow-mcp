# Structured View: Work Order Task (WOT)

> XRAY status: confirmed from classic form

## Identity

| Property | Value |
| --- | --- |
| ServiceNow table | `wm_task` |
| Common number prefix | `WOT` |
| Classic form | `wm_task.do` |
| Domain concept | Work Order Task |

## Structured fields

| Concept | Typical ServiceNow field | Notes |
| --- | --- | --- |
| Number | `number` | Human-readable task number |
| Parent Work Order | `parent` | Direct reference to parent `WO`; prefer display value |
| Company/customer | `company` | Reference; prefer display value |
| Location | `location` | Work/site location |
| State | `state` | Choice field; prefer selected display value |
| Dispatch group | `dispatch_group` | Dispatch/routing reference when used |
| Assigned to | `assigned_to` | Current technician/assignee |
| Due date | `due_date` | Task due timestamp |
| Short description | `short_description` | Human-readable summary |
| Description | `description` | Full task instructions/details |
| Work notes | `work_notes` | Journal input; activity stream is preferred for history |

Missing fields must be treated as optional rather than parser failures.

## Custom fields

Work Order Task forms can expose deployment-specific `u_*` fields. Examples of custom concepts include purchase-order references and catalog-item linkage. These should not be hardcoded into the generic DTO.

Custom fields may be retained through the same generic extension model used by other structured views:

```python
@dataclass
class CustomFieldDTO:
    name: str
    label: str | None
    value: str | None
    display_value: str | None
```

## Proposed structured representation

```python
@dataclass
class WorkOrderTaskDTO:
    sys_id: str
    number: str
    record_type: str = "wm_task"

    parent: str | None = None
    customer: str | None = None
    location: str | None = None

    state: str | None = None
    dispatch_group: str | None = None
    assigned_to: str | None = None

    due_date: str | None = None

    short_description: str | None = None
    description: str | None = None

    custom_fields: list[CustomFieldDTO] = field(default_factory=list)
    activities: list[ActivityDTO] = field(default_factory=list)
```

This is an XRAY/proposed representation, not yet a runtime API guarantee.

## Parent relationship

The parent Work Order is a first-class form field rather than a relationship inferred from text or navigation context.

Structurally:

```text
wm_task.parent                    → internal reference identifier
sys_display.wm_task.parent        → human-readable WO number
```

This confirms the stable relationship:

```text
WO / wm_order
  └── WOT[] / wm_task
          └── parent → WO
```

The parent reference is sufficient to navigate from a WOT back to its Work Order without relying on the page's list-navigation parameters.

## Relationships / related lists

The observed WOT form exposes relationship surfaces including:

- Service Management Incidentals / expense lines
- Sibling Tasks
- Task Activities
- Time Worked

These should remain explicit relationships rather than being eagerly embedded in the base `show_record` payload.

Conceptually:

```text
Work Order Task
├── Parent Work Order
├── Sibling Tasks[]
├── Incidentals[]
├── Task Activities[]
├── Time Worked[]
└── Activity Stream[]
```

## Activity stream

The WOT uses the same ServiceNow task-style journal/activity structure observed in the other task-derived records. Filters include concepts such as:

- comments
- work notes
- assigned-to changes
- attachments
- autogenerated/correspondence email events
- scheduling changes
- sidebar discussion/messages

The current `work_notes` textarea is an input surface, not the historical activity log. History belongs in `ActivityDTO`.

## Parsing strategy

```text
WOT number
   ↓
resolve wm_task
   ↓
GET wm_task.do?sys_id=<id>
   ↓
validate wm_task form structure
   ↓
parse stable fields
   ├── parent WO display value
   ├── reference display values
   ├── state display value
   ├── custom fields separately
   └── activity stream
   ↓
WorkOrderTaskDTO
```

## Generic form conventions confirmed

The WOT confirms the same classic-form conventions seen in the other record types:

```text
wm_task.<field>                     → raw/internal value
sys_display.wm_task.<field>         → human-readable reference value
sys_readonly.wm_task.<field>        → rendered readonly/choice value
sys_original.wm_task.<field>        → original form value
```

The form also exposes generic record identity metadata:

```text
sys_target       → table name
sys_uniqueName   → unique-key field name
sys_uniqueValue  → current record identifier
sys_displayValue → human-readable record number
```

These metadata fields are useful for a generic form validator and record-identity extractor independent of WOT-specific parsing.

## Navigation context

A WOT opened from a list can include navigation parameters describing the source list, row, total rows, target, and view. Those parameters are contextual UI state, not part of the record identity.

The canonical record read remains:

```text
wm_task.do?sys_id=<id>
```

The parser should therefore ignore list-navigation parameters when reading a known record.

## Discovery notes

This XRAY confirms the assumptions already used by the initial WOT implementation: `wm_task` is directly readable from classic server-rendered HTML, its parent Work Order is structurally available, reference fields expose display values, and journal history can be modeled independently from the form's journal input.

Together with the other structured views, the supported chain is now documented as:

```text
REQ / sc_request
  └── RITM[] / sc_req_item
        └── WO[] / wm_order
              └── WOT[] / wm_task
```

The next implementation step can use these four XRAYs to separate generic form extraction from record-specific typed adapters.
